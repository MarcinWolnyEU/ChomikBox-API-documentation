Login and session keep-alive

  • Auth returns the token that every later request carries as its first child. Right after it the client sends CheckEvents, starts the poll timer (the shortest active period wins: 300 s idle, 60 s while uploading, 15 s while a folder view is open), asks for Folders(0, 0), sends SessionBegin only if enabled (off by default) and flushes queued BoxEvents.
  • CheckEvents has no event list. Its only "event" is changes/folderModifyTime, a .NET tick count that moves after every folder change; a newer value makes the client reload the tree. The client reads only accountBalance, settings and changes and ignores new, which was nil in every live probe. Observed Live Polling, settings and events
  • The client never sends GetSettings; it sends SetSettings(downloadByBox) at start-up and on configuration changes. BoxEvents carries a few fixed events (shutdown, default-player and autostart changes) and is not off by default (C-09). Observed
  • More than three consecutive failed CheckEvents polls force a relogin (check-events-repeat-count = 3). A failed poll is not resent; the next timer tick sends a new one. Logout and CheckEvents are never retransmitted.
  • Live, several tokens of one account work at the same time, Logout ends only its own, and no expiry was seen within about 45 minutes (S-10). The password hash and the token travel in the clear (C-02, C-06); Forbidden and PermissionError reveal whether a user exists (S-01).

Operations: Auth, CheckEvents, Folders, Logout, BoxEvents. Mechanics: Protocol.

Folders - browsing and management

The client's folder tree marks the flags carried by FolderInfo: hidden, adult (+18) and passwd (password-protected).

Client vs live

  • The client reads prevModifyTime/modifyTime from every folder operation and refreshes when they disagree with its tree. Live, only ModifyFolder returns them; RenameFolder, MoveFolder and RemoveFolder return only status, and AddFolder only folderId. The tree is kept fresh through CheckEvents instead.
  • The client sends the public-upload flag as <public>; the server's parameter is publicUpload and it silently ignores public.
  • Folders depth: 0 is the whole subtree (586 nodes on the test account), 1 the node only, 2 the node and its children.
  • Three server behaviours need care: MoveFolder into itself faults yet moves the folder to the root (S-03); unknown ids fall back to the root (S-05); force=false still deletes folders that hold only subfolders (S-04). Folder passwords come back in plain text (S-02).

Operations: Folders, AddFolder, RenameFolder, MoveFolder, ModifyFolder, RemoveFolder.

Upload with resume

  • The upload server is whatever UploadToken names (sNNNN.chomikuj.pl:8084, a different one per ticket). The client builds a URL with key, stamp, folderId and fileName in the query, then posts to the path alone. By default it uses DirectNetworkReply, a raw socket speaking HTTP/1.0.
  • The multipart framing is non-standard: each part starts with a bare name="…" line, there is no Content-Disposition, and the file part must have no Content-Type line. The server parses parts by position, so any deviation corrupts the stored file. Live
  • The client reads filename and folderid from the reply; live, the server sends only res and fileid.
  • Thumbnails are generated when force-generate-thumbnails is set or the server asks for an image size; uploads with and without them were accepted. UploadToken does not validate the folder id (S-05), and everything travels over plain HTTP (C-01).

Operations: UploadToken, POST /file/, GET /resume/check/.

Download with agreements

  • An entry id can be a numeric file id, a file path /<user>/<folder>/<file>, or a folder path, which returns the folder with all its files and so works as a file listing, for other users' folders too. The <hamsterId>/<folderId> form, which the client builds for its own download folder action, makes the service fault, so that action presumably fails today (S-06). Live .<realId> is accepted (status Ok) but has never been shown to resolve a file, because only an unknown realId was tested. Unknown
  • The sequence element is optional. The client splits requests into parts of up to 2000 entries and collects all parts before it acts. A non-final part is acknowledged with Ok and only messageSequence; the final part carries the data, including the earlier parts' entries. Live This works only under conditions: the parts are stored per session (not per stamp) and never cleared, a final part with nothing stored gives Error, entries from two folders give an empty list, and only the final message's agreements count. Details in Protocol and S-13. Normal requests are single messages and unaffected.
  • size is approximate (512-byte granularity). Three agreement names were seen live. own (cost 0) is offered for your own files and was the only one accepted. small (cost 0) is offered for foreign files under 1 MB. transfer is offered for larger foreign files, with the cost in kB (floor of size/1024: a 1,694,208-byte file cost 1654); the account's transfer balance has the same unit. Each file got exactly one agreement. Live No foreign agreement was accepted and nothing was spent: only the offers were read. free, edu, points and access could not be triggered and stay Unknown live (names and units).
  • RefreshFileUrl was the only call that could carry expire, and it was always empty live. The client accepts only yyyy-MM-dd HH:mm:ss (local time) and uses it solely for the pause warning, with warn-before-expire in seconds. Observed
  • Signed URLs are reusable bearer URLs whose lifetime is unknown (S-08).

The downloader knows ten cost types, numbered 1 own, 2 small, 3 free, 4 edu, 5 access, 6 transfer, 7 points, 8 hdd, 9 queued and 10 mixed; AgreementInfo entries are sent for types 1 to 7.

Operations: Download, RefreshFileUrl, GET /File.aspx.

Music player - list and stream

  • FolderFiles lists audio files only, and only with disposition=player.audio: download gives WrongDisposition, other values Error. Folders without audio return an empty list. Items are <EntryInfo> with id, name, type, size.
  • For an MP3, Download with player.audio behaves like a normal download: agreement offer first, then a signed URL. RefreshFileUrl with player.audio also returns a URL.
  • The MusicFile.aspx template is never requested by the client; it is a 1.x cache identifier, and live it is gone (GET /MusicFile.aspx).

Operations: FolderFiles, Download, GET /File.aspx. Player internals: Architecture.

SavePlaylist - a playlist becomes a folder

  • The client only expects that a playlist folder is created or updated. Live, a playlist is an ordinary folder named after the playlist, inside a top-level folder Playlisty, and the items are copied: the folder holds the file under a new file id. Live
  • The client sends token, name, list, with the unused id of each PlayListItem set to -1. The server also accepts an optional sequence.
  • Playlisty is reused when it exists. A second call with the same name gives status = Ok and a new folder named <name>(1) (no space) with a fresh copy of the file under another file id. Live Playlisty itself has passwd = true and a server-generated password; the playlist folders have passwd = false and also a generated one.
  • FolderFiles on a playlist folder lists the copy as type = file. Live

Operation: SavePlaylist. Finding: S-02.

Browser click-catching - NPAPI to named pipe

  • The plug-in claims 31 MIME types of downloadable files. The pipe and the mutex names come from QtSingleApplication's naming scheme for the app id ChomikBox2.
  • The same pipe also receives commands from a second chomikbox.exe launch, for example after an Explorer verb or a chomik:// link (C-08).

Details: npcbplugin.dll, remote commands. Finding: C-12.
