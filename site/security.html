Security & privacy - findings register

  1. Overview
  2. Security & privacy

Every security-, privacy- and robustness-relevant finding of the project, in two parts: the shipped ChomikBox 2.0.8.2 client (C-01 to C-12) and the behaviour of the live chomikuj.pl service (S-01 to S-14). This page presents the full list with the evidence behind each entry.

Scope

  • The client findings come from examining the installed client and read-only inspection of one machine. No crash report and no update request were sent.
  • The service findings come from a small number of requests against the project owner's own account, inside throw-away sandbox folders. They describe what was observed; they are not the result of exhaustive testing, and no attempt was made to access other users' data.
  • A fault here means an unhandled exception while processing one request: the service answers that request with HTTP 500 and a WCF a:InternalServiceFault and keeps serving others. It does not mean the server went down.

Ratings and basis

High
Exposes credentials or control of the account.
Medium
Exposes private data, or can silently damage data.
Low
Information disclosure or a hardening gap.
Info
Behaviour worth knowing.
Basis
Observed in the client or in traffic, Live against the service, Inferred from observed facts, Unknown where not determined.

Ratings are a coarse guide for readers of this documentation, not a formal assessment.

Client - ChomikBox 2.0.8.2

Findings C-01 to C-12 concern the shipped client: how it handles credentials, tokens and user data, and what it sends where. This is a 2017 client looked at in 2026, so most points describe its design rather than a live risk.

C-01 All traffic uses plain HTTP

High

Every URL template in the client and its default config starts with http://: the SOAP service http://%1/services/ChomikBoxService.svc, the upload server http://<server>/file/ and resume check, signed download URLs, the web login hand-off, the session server, the crash collector http://bts.box.chomikuj.pl:8088/crash and the update repository. Observed

The SOAP service sits behind Cloudflare and also answers over HTTPS, but the client never uses it. Live

Why it matters. Anyone on the network path can read and change the password hash in Auth (C-02), the session token in every later request (C-06), folder passwords (S-02), file names, folder structure and uploaded content.

Open. The install ships gnutls, and https:// URLs are accepted as download arguments; whether the client uses TLS anywhere, and whether certificates are checked, is not known. Unknown

C-02 The credential is an unsalted MD5

High

Auth sends <passHash> next to the user name. The client computes it as QCryptographicHash::hash(password.toUtf8(), Md5).toHex(): lower-case hex MD5 with no salt. Observed The service accepts it. Live The client keeps the hash and sends Auth again at start-up, after the system resumes and on every relogin. Observed 

<Auth xmlns="http://chomikuj.pl/"><name>{{USERNAME}}</name><passHash>{{PASS_HASH}}</passHash><ver>4</ver>
  <client><name>chomikbox</name><version>2.0.8.2</version></client></Auth>

Why it matters. For this API the hash is the password: whoever captures it can log in without knowing the password. Inferred from the accepted Auth. Unsalted MD5 can be computed very quickly, so a leaked hash is open to offline guessing, and accounts with the same password share the same hash. C-01, C-03 and C-04 describe three ways the hash leaves the user's control. Operation page: Auth.

C-03 Stored credentials in conf.ini

Medium

%LOCALAPPDATA%\ChomikBox\conf.ini is a plain-text INI file. It holds [userinfo] login, password-hash and password-len, a section per saved account with the same keys plus password-remember, and [proxy] username and password. The hash is written when remember me is ticked. The live file has a userinfo section with these keys; the values were deliberately not copied. Observed

password-len records the length of the password, probably so the login form can show the right number of masking dots. Inferred

Why it matters. Any program running as the user, any backup of the profile and every crash report (C-04) carries a working credential for the account and, if one is configured, the proxy password.

C-04 What crash reports contain

High

After a crash, crashsender.exe posts a multipart form to http://bts.box.chomikuj.pl:8088/crash with the minidump and these files: message.log, conf.ini, the upload and download queues (local paths and file names) and the playlist, plus the text fields chomikId and chomikName. The only integrity value is the MD5 of <project>-<version>.<arch>. Observed argument list and field names; that conf.ini then contains the hash is Inferred from the default configuration. format API page

  • In GUI mode the user is asked first, but the question (It is possible to send debugging information back to developer team…) does not say that settings, credentials or file lists are included.
  • With --no-gui, which chomikbox.exe passes when an internal flag is set, the report goes out without asking. What sets that flag is Unknown.
  • message.log can be very large (134 MB on the inspected machine) and is uploaded whole if present (C-05).

Status. No report was sent during this project. On 2026-10-24 port 8088 accepted connections but gave an empty reply to HEAD; whether reports are still accepted or read is Unknown.

C-05 Verbose logging by default

Low

The default config value is [debug] level = 6, on a scale the config file explains as 0 - none, 1 - most important … 5 - a lot … 9 - garbage, dumps. On the inspected machine message.log had grown to 134 MB, with rotated copies in backup\. The SOAP layer logs lines such as message SENT (try N relogs M). ID: x (method); soap-debug and network-debug are off by default. Observed

Open. Whether tokens, hashes or request bodies reach the log was not analysed. Unknown The log matters because it travels with crash reports (C-04).

C-06 The session token in the clear

Medium
  • The token returned by Auth is the first child of every later request except SessionBegin, sent over plain HTTP (C-01). The serializer has a SOAP-header <Token> branch, but nothing enables it. Observed
  • The web hand-off opens http://chomikuj.pl/chomik/chomikbox/LoginFromBox?t={{TOKEN}}&returnUrl=/ in the browser. With a valid token the site answers with a redirect that sets a web session cookie (ChomikSession); t is the raw Auth token. Observed Live LoginFromBox

Why it matters. A token in a URL can end up in browser history, proxy logs and server access logs, and a captured token stays usable for at least as long as tokens were observed to live (S-10). Inferred An earlier note called t a one-time token; that is unverified. Unknown

C-07 Updates over HTTP, checked by an unkeyed hash, applied elevated

High
  • UUpdater fetches packages.xml and packages over plain HTTP from bts.box.<domain> or download.box.<domain> and follows redirects. packages.xml is parsed with no hash and no signature check. Observed
  • Each downloaded file (for .gz files, the decompressed content) is hashed with SHA-1 and compared with the sha1 attribute of that same packages.xml. A mismatch is the message Signature error, but there is no signature and no embedded key: the only cryptographic API the client imports is QCryptographicHash. The expected hash arrives over the same unauthenticated channel as the file, so the check detects corruption and truncated downloads, not an attacker who controls that channel. Observed
  • installer.exe has a requireAdministrator manifest and is started through BProcess::runAsAdministrator, which uses the runas verb when the target's manifest asks for administrator rights. It copies files, runs the commands listed in the package (Executing command) and writes HKLM keys, and it runs those commands without any prior check of the package. Its own post-copy SHA-1 of the installed files only decides whether a package gets the installed mark: no error, no rollback. Observed
  • An optional SHA-1 check of existing files is off by default (check-hash-for-exiting-files = false). Observed

Why it matters. Anyone who can alter the traffic (a hostile network, DNS, a proxy) can supply a matching packages.xml and package, and the package's commands then run elevated. A network attacker does not need the real server. That is why the finding is rated High, on the condition that it needs a position on the network path. Inferred

Status. The repository answered 404 and 403 on 2026-10-24, so the path is dormant on current installs. Inferred Which updater executable a real repository would nominate is data in packages.xml and cannot be determined from the client. Unknown

C-08 Local command surface

Low
  • The named pipe \\.\pipe\qtsingleapp-Chomik-739b-<sessionId> has a predictable name and accepts the same commands as the Explorer verbs: upload a path (-u), download a URL (-d), add to the playlist (-p) and folder operations including --folders remove --force. Observed
  • The chomik:// protocol hands text chosen by a web page to the same parser, Application::executeRemoteCommand, which accepts chomik://file:, chomik://folder: and chomik://files/ forms. Observed Windows integration
  • The pipe also accepts --file-server <host>, which makes the running client send all uploads and resume checks, upload keys included, to that host instead of the server chosen by the service. That the verb is accepted over the pipe is Observed; that the value reaches the upload code is Inferred (the link to the upload path was not fully confirmed).

Open. The pipe's access control, how the parser treats unexpected input, and which commands a chomik:// URL can actually trigger were not analysed. Unknown

C-09 Usage data with event polls

Info
  • Every CheckEvents call (every 300 s when idle, every 60 s while uploading, every 15 s while a folder view is open) carries stats{isUploading, isPlaying, isDownloading, panelSelectedTab, animation}. Observed CheckEvents
  • BoxEvents sends Event{name, value} pairs, kept in [proto-box] box-events while the client is logged out. It is not GUI click statistics and it is not off by default: nothing gates it. A small fixed set of events is sent whenever its trigger occurs: shutdown (poweroff, suspend or quit, after the user chose an action for when transfers finish), detected.defaultplayer, settings.defaultplayer and settings.autostart. The client sends no other event names. Observed The service accepts real event names with status Ok; whether it stores them is Unknown. Live BoxEvents
  • When the session server is enabled, SessionBegin also sends the user name, the password hash and an OS description; that is off by default (S-12). Observed
  • On the server side, Download results that contain files set a guid cookie with a two-year expiry; whether the Qt client keeps cookies was not analysed. Live

C-10 Integrity checks, not authentication

Info
  • base.ini [main] key is a checksum over the [main] section of base.ini, verified at start-up; on a mismatch the client stops with qFatal("HACKING! base.ini/main corrupted."). Observed
  • The crash report's checkSum is the MD5 of <project>-<version>.<arch>, a constant per build, with no key. Observed

Neither proves who sent or edited something: they stop casual edits and accidental junk, not a deliberate actor. Inferred

C-11 Internal addresses in the client

Info
  • chomikbox1conf.exe contains the private address 192.168.10.30. Observed
  • The default config shows an application default of 192.168.10.49 for [proto-webox] webservice-host, and the client has a built-in main address 208.43.39.225. webservice-main is used only when webservice-redirect = true, a development setting that is off in the default config. Observed

These look like development and test leftovers; none of the addresses were probed. Inferred

C-12 Obsolete browser plug-in

Info

npcbplugin.dll registers itself in NPAPI browsers for 31 MIME types, among them application/x-msdownload, application/exe and application/x-msdos-program, and forwards the URLs to ChomikBox. Observed Current browsers dropped NPAPI years ago, so it no longer loads. Inferred Its cold-start path reads an HKLM value that a plain MSI install never writes. Observed Components, flow

Service behaviour observed live

Findings S-01 to S-14 describe how the chomikuj.pl service answered during the live verification of 2026-10-24 and 2026-10-25. Only the project owner's own account was used, write operations stayed inside sandbox folders that were removed afterwards, and each case is backed by a captured, redacted exchange under api/examples/, linked here through its API reference page. These are observations, not the result of exhaustive testing.

S-01 Account enumeration via Auth

Medium

An unknown user name gets status = Forbidden; a known user name with a wrong password gets PermissionError. In both cases hamsterId is 0 and every other member is nil. Live, with one deliberate wrong-password attempt.

Why it matters. The difference tells anyone whether an account name exists. The client itself shows the same credentials dialog for both.

Evidence: api/examples/Auth/unknown-user.*, api/examples/Auth/wrong-password.*; see unknown user and wrong password

S-02 Folder passwords in plain text

Medium
  • ModifyFolder echoes a newly set folder password in <password> (and sets passwd to true).
  • Folders lists each folder's password. Confirmed by the reviewer's read-only full-tree listing of the account: 1 of 586 folders has passwd = true, and its password came back non-empty in plain text. The value was neither printed nor stored. Live
  • The folder that SavePlaylist creates gets a server-generated password while passwd stays false.

All of this travels over plain HTTP (C-01). Live In the captured examples these values are redacted to {{FOLDER_PASSWORD}}, except the password the capture tool itself set on a throw-away sandbox folder.

Evidence: api/examples/ModifyFolder/set-password.*, api/examples/Folders/playlist-folder.*; see ModifyFolder set-password and Folders playlist-folder

S-03 A MoveFolder fault that does not roll back

Medium

MoveFolder with newFolderId = folderId (a folder into itself) returns HTTP 500 with a:InternalServiceFault, an unhandled exception for that request, yet the folder has still been moved to the account root. Live During testing the sandbox folder was found at the root and moved back.

Why it matters. A client that treats the fault as "nothing happened" ends up with a folder in an unexpected place. Integrity rather than confidentiality.

Evidence: api/examples/MoveFolder/into-itself.*, api/examples/MoveFolder/recover-from-root.*; see into-itself and recover-from-root

S-04 RemoveFolder with force=false

Medium

force=false only protects folders that contain files: such a folder gives NotEmptyOrNotExistsFolder and nothing is removed. A folder that holds only subfolders is deleted together with all of them, with status = Ok. Live

Why it matters. Anyone using the API who reads force=false as "only if empty" can lose a whole folder tree.

Evidence: api/examples/RemoveFolder/not-empty-without-force.*, api/examples/RemoveFolder/with-files-without-force.*; see not-empty-without-force

S-05 Silent fallbacks to the root folder

Low-Medium
  • Folders with an unknown folderId returns the root folder with status = Ok.
  • MoveFolder to an unknown parent moves the folder to the root, with status = Ok.
  • UploadToken with an unknown folderId still issues a full upload ticket.

Live A client should validate ids itself and check the id it gets back.

Evidence: api/examples/Folders/nonexistent-folder.*, api/examples/MoveFolder/nonexistent-target.*, api/examples/UploadToken/nonexistent-folder.*; see Folders, MoveFolder, UploadToken

S-06 Dropped parameters and unhandled faults

Low
  • WCF reads parameters forward only: an out-of-order parameter, or one in the wrong namespace, is silently treated as null or 0 instead of being rejected.
  • Some malformed requests end in an unhandled a:InternalServiceFault (HTTP 500): an operation element in http://chomikuj.pl without the trailing slash, the <hamsterId>/<folderId> form of a Download id, and an empty Auth body.
  • The client's own download folder action builds exactly that <hamsterId>/<folderId> id (%1/%2, hamster id first), and its id builder prefers it over the folder path, which does work. That feature therefore presumably fails against today's server. Observed in the client, Inferred as to the outcome.

Live

Evidence: api/examples/Download/id-hamster-slash-folder.*, api/examples/Auth/empty-request.*, api/examples/Service/wrong-operation-namespace.*; see Download, Auth, SOAP endpoint behaviour

S-07 Contract disclosure through faults and headers

Low
  • a:DeserializationFailed names the expected parameter and its CLR type, for example TeamSolutions.Chomik… types. This reveals the exact parameter names, types and order without a WSDL.
  • a:DestinationUnreachable, returned for an operation name appended to the URL path, leaks internal origin host names such as vmain50.hwsl.local:8080 and vmain53.hwsl.local:8080.
  • Responses carry x-powered-by: ASP.NET, x-aspnet-version: 4.0.30319 and x-server: m50, m52, ….

Live On the other side, WCF metadata publishing is disabled (no WSDL), and the generic faults carry no exception detail.

Evidence: api/examples/Service/deserialization-failed.*, api/examples/Service/rest-style-path.*; see SOAP endpoint behaviour and path-style URL

S-08 Bearer download URLs

Low

Signed download URLs (http://sNNNN.chomikuj.pl/File.aspx?e=…&pv=…) work for whoever holds them: a repeated GET and a Range request both succeeded. The expire field was always empty, so how long a URL stays valid is Unknown. Live

Evidence: api/examples/FileDownload/*; see GET /File.aspx and RefreshFileUrl

S-09 Anonymous image access by id

Info

http://chomikuj.pl/Image.aspx?id=<fileId> answers with a 302 redirect to a signed file URL without any session. This was observed for the owner's PNG in a folder without a password; password-protected folders were not tested. Live File ids are numeric and sequential, and public hosting is the purpose of the service, so this is rated Info.

Evidence: api/examples/Web/image-aspx.*; see GET /Image.aspx

S-10 Session model

Info

Several sessions of one account are valid at the same time; a new Auth does not invalidate earlier tokens. Logout invalidates only its own token. No expiry was observed within the longest test window of about 45 minutes; longer lifetimes were not measured. Live

Evidence: api/examples/CheckEvents/concurrent-session-first-token.*, api/examples/CheckEvents/first-session-after-other-logout.*; see concurrent session and Logout

S-11 Client identity not enforced

Info

Auth accepts any ver and works without the client element, so any program can present itself as ChomikBox. Live

Evidence: api/examples/Auth/protocol-version-1.*, api/examples/Auth/without-client-element.*; see protocol-version-1 and without-client-element

S-12 An obsolete session host in the client

Low

The client's optional session server, session.box.chomikuj.pl (SessionBegin), no longer resolves in DNS. Live If someone registered that name, an old client with [proto-webox] session-enabled = true would send it the user name and password hash. That setting is off by default. Inferred risk. No credentials were sent to any session host during this project.

Evidence: api/examples/SessionBegin/main-endpoint-not-supported.*, api/examples/Web/session-server.*; see SessionBegin

S-13 Sequenced Download state is per session

Low
  • A Download request can be split into parts (messageSequence). The service stores the entries of each non-final part per session token, not per stamp, and does not clear them when the final part arrives. A new part 0 replaces what was stored.
  • A final part with nothing stored in the session returns status = Error with no error message. If the combined entries span two folders, it returns status = Ok with an empty list, not even its own entry. A stale part from another folder empties a later final part in the same way.
  • Agreements count only in the final message. The single-message form (count = 1) ignores stored parts.

Live (26 sequenced exchanges in four sessions; the storage mechanism itself is Inferred.) Why it matters. A client that reuses a session for two sequenced requests can get wrong or empty results without any error, so this is a correctness rating. The real client sends single messages unless a request holds more than 2000 entries, so normal use is unaffected. Inferred

Evidence: api/examples/Download/sequence-*, seq1c-*, seq1d-*; see Download

S-14 ModifyFolder ignores description and price fields

Info
  • ModifyFolder accepts description, freePoints and freeTransfer: any in-range value, including -1, 2147483647 and a 10,000-character description, returns status = Ok and moves modifyTime. Nothing is echoed, Folders never returns a value, and no effect was visible in the download offer, the public pages or the balance. Live
  • Out-of-range or non-numeric values (overflow, abc, an empty element) fault during deserialization with a:DeserializationFailed. Live
  • The client never sends these fields: its folder dialog has widgets for them but hides them. Observed

A caller that sets a folder price or description through the API gets a success status and no effect, which is easy to mistake for a stored setting. Whether the service writes the values somewhere it never exposes is Unknown.

Evidence: api/examples/ModifyFolder/set-*, description-*, free-*, full-form-*; see ModifyFolder

Handling and mitigating observations

How the project handled the account

  • Credentials were read only at run time. Every captured artefact is redacted with placeholders, and independent leak scans found no credential values in project files.
  • Live writes were confined to _chomikbox_api_test* sandboxes and checked against a full-tree snapshot. Two server behaviours (S-03, S-05) briefly moved a sandbox folder to the root; it was moved back and deleted each time.

On the other side

  • The WCF service publishes no metadata (no WSDL), and its generic faults carry no exception detail. Live
  • In GUI mode the crash reporter asks before sending. Observed
  • Downloads that cost transfer or points open an agreement window that shows the cost first; links outside chomikuj.pl get one too. Observed
  • The optional session server is off by default. Observed

Unknowns that matter most

  • Any use of TLS in the client (gnutls is shipped) and certificate checking.
  • Access control on the named pipe; how executeRemoteCommand handles hostile input and what a chomik:// URL can reach.
  • Whether logs contain tokens or hashes.
  • Which updater executable and package commands a real repository would nominate (the update check itself is described in C-07).
  • Token and signed-URL lifetimes; the server-side state of the crash collector.
