Architecture - processes and layers

  1. Overview
  2. Architecture

ChomikBox is one long-running Qt 4 GUI process plus a handful of short-lived helpers. Inside the main process the code is layered: module windows on top, an application object that owns the single-instance channel and the updater, a transfer layer, and a SOAP stack that turns method calls into HTTP POSTs.

This page follows that structure from the outside in. Component-by-component detail is on Components; the wire format is on Protocol.

Processes - what runs where

Only two executables ever talk to the network: chomikbox.exe and crashsender.exe. The others run locally and start only when something specific happens: an install, an update, a crash, or a manual start.

  1. 1After a fresh install the MSI runs "[SystemFolder]Cmd.exe" /c "start /b chomikbox1conf.exe" (custom action ExeCaKeyF01, condition not Installed). Observed
  2. 2The finish page can launch ChomikBox.exe (CaLaunchProductCheckBox). Observed
  3. 3Shortcuts, the autostart Run value, Explorer verbs and chomik:// links start chomikbox.exe. If an instance already holds the lock (7), the new process hands its command line over the named pipe and exits. Observed
  4. 4The browser plug-in writes -d<url> into the same pipe, or cold-starts the exe through ShellExecute when no instance is running. Observed
  5. 5UUpdater starts installer.exe elevated (BProcess::runAsAdministrator), also for browser plug-in installs (--plugmode). After an update the installer restarts ChomikBox with --update=success or --update=failed. Observed
  6. 6The Breakpad callback writes a minidump and runs crashsender.exe via ShellExecute. Observed
  7. 7The running instance owns the QtSingleApplication lock file and listens on the named pipe. Observed
  8. 8configurator.exe checks the lock file and refuses to start while ChomikBox is running. Observed

Qt 4 application - structure

chomikbox.exe, configurator.exe and chomikbox1conf.exe are built on the same in-house framework: a BaseApplication class that resolves the data folder, checks base.ini, loads skins and translations and reads the configuration. On top of it each executable has its own application class: Application in chomikbox.exe and configurator.exe, ChomikBox1 in chomikbox1conf.exe. Observed

Start-up, as far as it is known

  1. Data location. BaseApplication::__init takes base.ini [main] data-location (which may use ${app} and ${cwd}), lets --data-location <dir> override it, and otherwise falls back to QDesktopServices::storageLocation, which on Windows is %LOCALAPPDATA%\<title>. Failures log data location is not writable. Observed
  2. Integrity check. The key in base.ini [main] is a checksum over that section, verified at start-up; on a mismatch the client calls qFatal("HACKING! base.ini/main corrupted."). Observed
  3. Configuration. Built-in defaults come from the embedded :/default/defconf.ini and the brand file :/default/defconf-<domain>.ini; user values come from conf.ini (see Configuration system).
  4. Skin and locale. skins/app/<name>.skin is registered with QResource::registerResource() under /skin; the default is green2 (green for Russian). Translations come from locale/*.qm. Observed
  5. Single instance. QtSingleApplication with the id ChomikBox2 (see IPC).
  6. Plug-ins. The Application constructor loads tsplugins/integration/*.tsp and checks tsbox_plugin_qt_build before use. Observed

Shared command-line options

Every framework-based executable accepts --silent, --config <file> (alternative conf.ini), --base-config, --data-location <dir>, --standalone, --debug / --nodebug, --log / --nolog and --skin <name>. The commands that chomikbox.exe itself understands are listed on Components. Observed

Windows of the GUI

Every window is a frameless BWindow drawn from a 9-slice image (dialog.png or window.png) and styled by a Qt style sheet that ships inside the skin: panel.css, uploaderWindow.css, downloaderWindow.css, playerWindow.css, folderWindow.css, fileWindow.css, settingsWindow.css, downloadAgreementWindow.css, minimenu.css, plus the global qt.css. Module windows default to 359×450 pixels; the config comment says that size was chosen because of netbooks. Observed

Networking - layers of the SOAP client

Calls to the chomikuj.pl service pass through four layers of classes, each with one job. The class roles below are Observed; the wire format itself is on Protocol.

Classes of the SOAP client
ClassRole
NetProtoBoxEverything specific to chomikuj.pl: one builder per SOAP operation (18 in total), the response dispatcher messageResponse, the CheckEvents timer, and the upload and resume-check HTTP requests. setService sets the action URL http://chomikuj.pl/IChomikBoxService, the method namespace http://chomikuj.pl/ and the service URL http://%1/services/ChomikBoxService.svc.
NetModuleSoapsendSoap and sendSequencedSoap; owns the BSoapManager. Reads the per-message properties soap:actionUrl, soap:method, soap:args, soap:url, soap:methodUrl and soap:gzip, and builds SOAPAction as action URL + / + method.
NetModuleThe message pool: message ids, repeat and relog counters, timers for resending and for dropping stale messages, and the relogin procedure.
BSoapManagerA QNetworkAccessManager subclass: base URL, SOAPAction header, optional gzip compression of the request body.
BSoapMessage, BSoapValueThe envelope as a tree of values; serialised with QXmlStreamWriter, with no indentation and with i:nil="true" for null values.
BSoapParserSAX parser: compares lower-cased local names and ignores prefixes and namespaces; expects Envelope, Body, an element ending in Response (or Fault) and one ending in Result; walks arrays by index.
NetFileHTTP reply wrapper for downloads, with timeouts and Range support.
DirectNetworkReplyRaw-socket HTTP/1.0 client used for direct uploads (POST <path> HTTP/1.0).

Life of a request

  1. A builder in NetProtoBox creates the arguments, always starting with token except for Auth and SessionBegin, and sets client-side flags such as :sessionBound or :noRetransmit. These flags are never sent.
  2. NetModule enqueues the message and assigns :messageId, :repeatCount and :relogCount = 0. :loginRequired defaults to true.
  3. NetModuleSoap serialises the envelope and BSoapManager POSTs it with Content-Type: text/xml;charset=utf-8, the raw SOAPAction header and, when soap:gzip is set, a gzip body with Content-Encoding: gzip.
  4. NetProtoBox checks the response status: Ok goes to the handler for that method name; BadToken triggers a relogin; anything else becomes an error that carries errorMessage.
  5. On relogin, queued messages marked :sessionBound are dropped; the rest are kept and resent with the new token, which replaces the token element in place.

The modules never build requests themselves. They call NetProtoBox slots through Qt signals (login, sendCheckEvents, sendGetFolders, sendFolderAdd and the other folder operations, sendUploadToken, sendRefreshFileUrl, sendSavePlaylist, sendSetSettings, sendGetSettings, sendBoxEvents), and NetProtoBox answers with signals such as logged, foldersAvailable, folderFiles, fileListAvailable, uploadTokenAvailable, uploadError, refreshFileUrl and accountBalanceChanged. Messages tagged resume/check or upload-file leave the pool through NetFile or DirectNetworkReply instead of the SOAP path. Observed

Large Download requests are split into a sequence of messages that share a random stamp (sequence{stamp, part, count}, at most 2000 entries each by default), and the client waits for every part before it acts on the result. Observed Details: Protocol.

SOAP replies time out after connection-timeout (20 s, clamped 5–120 s). The [proxy] settings (HTTP or SOCKS5) are applied as the application-wide Qt proxy. Observed

Transfers - queues and file I/O

Uploads and downloads are queue items (NetReqFile) shown in tree views backed by NetReqFileModel. Each account has its own queue, saved as queue-upload-<hamsterId>.ini and queue-download-<hamsterId>.ini. Writes to these files are batched with a short delay: 350 ms for uploads and 650 ms for downloads. Observed

A queue item records state, action, fileId, fileName, folderId, folderPath, size, local folder and file name, expire, bytesTransmited (sic), extraKeys and modification dates. The class also knows directUrl, fileRealId, hamsterId, hamsterName and types. Observed

What the configuration reveals

  • Direct upload. [proto-box] direct-upload = true (direct connection when sending files) sends uploads through DirectNetworkReply, a raw socket speaking HTTP/1.0, with its own socket buffer (directnetworkreply-so_sndbuf = 32 KiB) and write buffer (8 KiB, sized dynamically). When a proxy is configured, force-access-manager-if-proxy = true makes uploads go through QNetworkAccessManager instead. Observed
  • Throttling. Upload speed limits are applied to the device the file is read through (device->setReadLimitK(…) in uploaderwindow.cpp). Observed That device is probably the class in ../utils/ioproxydevice.cpp. Inferred
  • Upload retries. Up to 5 quick retries after network errors (send-retry-count), then slow retries up to send-retry-max = 17, skipping send-retry-break = 20 attempts in between; the retry delay is 15 s. Observed
  • Downloads. 5 slots, 5 extra slots for files fetched out of order, one connection per file (max-connection-count = 1 hides the multi-connection option), a stalled network timeout of 30 s and a resume retry after 300 000 ms. Observed
  • Thumbnails. The upload request has fields for thumbnails (thumb, medthumb and their dimensions), rendered with thumbImageBuffers at quality 82. They are generated only when [proto-webox] force-generate-thumbnails = true or when the server asked for an image size, and a resume check can tell the client to skip them. Observed

All keys and defaults are listed on Configuration.

Media stack - the music player

The player module (Muzyka) consists of PlayerWindow, a PlaylistModel and a PlayerCache. Decoding uses GStreamer 0.10 with plug-ins in gplugins\ and ffmpeg. Observed

  • Sources. Local files (Explorer verb -p"%1", file associations) and files on the service. For the latter the player requests file URLs with the disposition player.audio and streams them with a plain GET carrying Icy-MetaData: 1; a reply is accepted only with HTTP 2xx, a non-zero length and no x-nofile header. Observed The MusicFile.aspx?chomik_id={chomikid}&sess_id={sessid}… template is never requested by the client: it is an identifier written to cache.cfg for 1.x compatibility. Observed
  • Playlists. Saved to the account with SavePlaylist: a name plus PlayListItem{id, realId} entries in which exactly one of the two ids is real and the other is -1. Locally the playlist is playlist.m3u8. Observed
  • Cache. Downloaded tracks are cached under cache\player\ (index cache.cfg), with a default limit of 10 GiB ((qint64)10 * 1024 * 1024 * 1024). The first run of 2.x offers to import the 1.x player cache. Observed
  • Media keys. Global shortcuts for Play, Stop, Next and Previous are on by default; Volume Up, Volume Down and Mute are off. Observed
  • Default player. ChomikBox can make itself the default music player through UserChoice ProgIds, elevating when needed (see Windows integration). Observed
  • Desktop hamster. While music plays, the desktop hamster switches to its headphones animation (player-playing condition). Observed

How the player drives GStreamer (directly or through a Qt multimedia wrapper) has not been analysed. Unknown

Single instance and IPC

ChomikBox uses Qt Solutions' QtSingleApplication with the application id ChomikBox2. The library derives every object name from qtsingleapp-, the first six letters of the id (Chomik), a CRC-16 of the id (739b) and the Windows session id. Observed

Inter-process objects
ObjectNameUsed for
Lock file%TEMP%\qtsingleapp-Chomik-739b-<sessionId>-lockfileHeld by the running instance (QtLockedFile); configurator.exe checks it. The file is 0 bytes and can be left behind.
Named pipe\\.\pipe\qtsingleapp-Chomik-739b-<sessionId>Remote commands to the running instance (QtLocalPeer); exists only while the app runs.
MutexChomikBox2Probed by the browser plug-in (CreateMutexA then ERROR_ALREADY_EXISTS) to decide whether ChomikBox is running.
MutexChomikBoxMutexChecked by 2.x to detect a running ChomikBox 1.x (Application::oldBoxIsRunning).

A message on the pipe is a Qt QDataStream::writeBytes frame: a 4-byte big-endian length followed by the text, as the browser plug-in sends it (-d + URL + NUL). The receiver is Application::executeRemoteCommand, which splits the text into tokens and handles upload, download, playlist and folder commands as well as chomik://, http(s):// and file: URLs. A queued command line can also be kept in [application] remote-command. Observed

The delivery paths are drawn on Windows integration; the command list is on Components.

Configuration system

Every setting is looked up by section and key, together with an application default (for example 15 for [network] connection-timeout). Values come from INI files, not from the registry.

  1. Application default, the value the application supplies when it reads a key; used only when no later layer defines the key.
  2. Default config :/default/defconf.ini, 62 841 bytes with 43 sections, built into both chomikbox.exe and configurator.exe (identical in both). Its values overwrite the application defaults.
  3. Brand overlay :/default/defconf-<domain>.ini, chosen by base.ini [main] domain. For chomikuj.pl it changes only web URLs and two cost flags.
  4. User file %LOCALAPPDATA%\ChomikBox\conf.ini, written through QSettings in INI format (UTF-8).

The order of 2 and 3 is Inferred: the application builds the brand path and falls back to the generic file, and the brand file holds only a few keys. QSettings touches the registry only for the autostart Run value and file associations; there is no HKCU\Software\<org> key. Observed

Keys, defaults and the brand overlays are on Configuration.
