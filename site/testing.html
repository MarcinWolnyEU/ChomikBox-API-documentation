PHP client and tests

  1. Overview
  2. PHP client & tests

The project's third output is a PHP 8.3 library that speaks the ChomikBox protocol, both the SOAP service and the file-server HTTP calls. It comes with three PHPUnit suites: one tests the library on its own, one checks it against the OpenAPI document, and one runs it against the real service inside a sandbox.

Source: php/README.md.

Client architecture - php/src/

Namespaces of the library (PSR-4, ChomikBox\)
PartRole
ChomikBoxClientHigh-level client: one method per implemented SOAP operation (17), each returning a typed result, plus webLoginUrl() for LoginFromBox and fetchFile() for signed file URLs, with the player's header variant
Soap\Envelope builder (Envelope, SoapStruct, SoapList), SoapClient (headers, optional gzip body), response parsing (SoapResponse, XmlNode) and SoapFault
Http\Transport interface and the cURL implementation; tests swap in a fake transport
Model\Typed results: AuthResult, FoldersResult/FolderInfo, DownloadResult/FileEntry/AgreementInfo, UploadTokenResult, …
Upload\Uploader (UploadToken, resume check, POST), ChbMultipart (the client's !CHB multipart format, byte for byte), RespXml
Spec\OpenApiContract and XmlSchemaWalker: load the per-operation spec (api/chomikbox.per-operation.openapi.json, else api/chomikbox.openapi.json; the strict document is loaded explicitly where needed) and validate XML and multipart bodies against an operation's schema. A PHP port of api/tools/lib/xmlwalk.mjs
Recorder\Recorder (writes captured exchanges as example files), Redactor (replaces secrets with placeholders, fails closed), LeakScanner
CredentialsReads ../credentials/chomikuj-{username,password,email}.txt at run time; values are never printed

By default the client reproduces the real client's wire form: gzip body, s:encodingStyle, booleans as 0/1, upload boundary !CHB<stamp>. Options switch to plain SOAP, which the service also accepts. Non-Ok statuses are ordinary answers, not exceptions; real SOAP faults (HTTP 500) are thrown as SoapFault.

$client = ChomikBoxClient::create();
$auth   = $client->auth(Credentials::fromDirectory());   // Forbidden = unknown user, PermissionError = wrong password
$tree   = $client->folders(0, 2);                        // depth: 0 = all, 1 = node only, 2 = node + children
$folder = $client->addFolder(0, 'my-folder');            // newFolderId = parent id
$up     = (new Uploader($client))->upload($folder->folderId, 'a.txt', "hello\n");
$ask    = $client->download([new DownloadRequest($up->fileId())]);   // lists agreements, url = null
$client->logout();

Test suites - what each guarantees

PHPUnit suites (php/phpunit.xml)
SuiteNetworkGuarantees
Offline
tests/Offline		noneEnvelope and serialisation details (nil, booleans, escaping, list items, namespaces); parameter names and order for every operation, which matters because WCF silently drops out-of-order parameters; the !CHB multipart layout and resume; redaction and leak scanning; parsing of every captured example under api/examples/
Contract
tests/Contract		none; needs both spec documents under ../api/(a) every request the client builds, in both wire modes and for several argument sets, validates against the operation's request schema, with SOAPAction, method, media type and URL as in the spec; (b) every spec example validates against its schema and the client parses every response example; (c) every operationId maps to a client method or a documented skip, and every SOAP operation has a Live test or a reason; (d) the spec's servers and paths equal the client's constants. WalkerSelfTest proves the walker rejects violations, so these tests cannot pass vacuously. Strict document (128 tests, StrictDocumentTest): every SOAPAction the client sends is in the callSoapService enum and its URL is the strict server and path; every client-built request matches exactly one oneOf branch, the one x-soap-operations names; every strict response example validates against the schema its entry names. Upload replay (16 tests, UploadCaptureReplayTest): the client reproduces all six captured upload bodies byte for byte, and mutated bodies (a Content-Type on the file part, LF instead of CRLF framing, swapped part order) are rejected.
Live
tests/Live		the real service, opt-inSession and polling, settings read and identical write-back, BadToken from every operation, the folder lifecycle, upload and resume check, a download round trip with the own agreement, audio listing and streaming, a forged upload key, BoxEvents and a deserialization fault, and logout of one session. Every request and response is validated against the spec, and the account-tree fingerprint must be identical before and after.

Running the tests

cd V:\Improve\Chomikuj\php
composer install
vendor\bin\phpunit --testsuite Offline                          # no network
vendor\bin\phpunit --testsuite Contract                         # no network, needs ..\api\chomikbox*.openapi.json
$env:CHOMIK_LIVE = "1"; vendor\bin\phpunit --testsuite Live     # real service, needs ..\credentials\*.txt
php tools\leak-check.php                                        # redaction check of everything written
  • On a POSIX shell: CHOMIK_LIVE=1 vendor/bin/phpunit --testsuite Live. Without CHOMIK_LIVE=1 the Live tests are skipped.
  • CHOMIK_SPEC_FILE overrides the per-operation spec, CHOMIK_STRICT_SPEC_FILE the strict canonical document, and CHOMIK_EXAMPLES_DIR the examples directory.
  • php tools\capture.php regenerates api/examples/ against the live service in a throw-away sandbox; tools\capture-audio.php covers the MP3, player.audio and SavePlaylist cases.

Safety model for live tests

The live account belongs to a real user, so live work follows strict rules:

  • Sandbox. The Live suite creates _chomikbox_api_test_live_<timestamp> at the account root, works only inside it and removes it with force=true in its last test. Pre-existing folders and files are never renamed, moved or deleted.
  • Snapshot and diff. That last test compares a fingerprint, a SHA-256 over the id, name and parent of every folder, taken before and after the suite. The one successful SavePlaylist call, which necessarily writes outside the sandbox (Playlisty/<name>), was made once by capture-audio.php under full-tree snapshots: exactly two new folders appeared, both were removed, and the tree then equalled the pre-run snapshot. The Live suite tests only the BadToken path of SavePlaylist.
  • No spending. Only the free own agreement is accepted, only for files the tests uploaded themselves; the account balance was unchanged. SetSettings writes back the value just read.
  • Gentle traffic. Requests are sequential. Only tiny generated files are uploaded (text, a small PNG, a one-second silent MP3), and only those are downloaded. There was at most one deliberate wrong-password login.
  • Leak check. Credentials are read only at run time. Redactor replaces secrets with placeholders ({{USERNAME}}, {{PASS_HASH}}, {{TOKEN}}, {{UPLOAD_TOKEN}}, {{STAMP}}, {{SIGNED_URL}}, {{COOKIE}}, {{FOLDER_PASSWORD}}, …) and refuses to write a file in which a known secret survived. tools/leak-check.php compares every file under php/, api/ (both spec documents and the examples), site/ and the scratch notes against the real credentials, checks captures for un-redacted values, and reports file, rule and line only.

Two server behaviours briefly moved a sandbox folder to the account root during testing (S-03, S-05); it was moved back and deleted each time.

Spec coverage - operationId to client

The per-operation view of the spec has 36 operations (the strict document has the same content in 19, with the 17 SOAP operations and the endpoint behaviour folded into callSoapService). The client implements 17 SOAP operations and maps loginFromBox to webLoginUrl(), downloadFile to fetchFile(), and uploadFile and resumeCheck to the Uploader. The other 15 operationIds are documented skips in tests/Support/SpecSupport.php:

  • SessionBegin: its host has no DNS record, and credentials are never sent there (S-12).
  • Probes and infrastructure: GET /session, HEAD /File.aspx, GET ….svc, endpoint behaviour, path-style URL.
  • Pages opened in a browser: legacy LoginFromBox, registration, lost password, Image.aspx, MusicFile.aspx.
  • Unverified client components: the crash reporter and the three updater URLs.

The PHP walker does not check the three unverified multipart/form-data crash-report examples.

Validating the spec - api/tools and Redocly

There are two OpenAPI 3.2.1 documents. api/chomikbox.per-operation.openapi.yaml is the authoring source and per-operation view (one path item per SOAP operation, with the ?op= server deviation declared in x-oas-deviation). api/chomikbox.openapi.yaml is the strictly conformant canonical document, generated from it by build-strict.mjs: SOAP is one POST with a SOAPAction enum and oneOf bodies. The strict document is never edited by hand.

cd V:\Improve\Chomikuj\api\tools
npm install                      # once: yaml, ajv, ajv-formats, saxes, @hyperjump/json-schema
node sync-examples.mjs --check   # optional: captures vs the source
node build-strict.mjs            # regenerate the canonical strict document from the per-operation source
node validate.mjs                # checks (a)-(h) on each document, (i) across both; writes both .json files

cd V:\Improve\Chomikuj\api
npx -y @redocly/cli@latest lint chomikbox.openapi.yaml chomikbox.per-operation.openapi.yaml --max-problems 1000

cd V:\Improve\Chomikuj
node site\tools\build-api.mjs    # regenerate the site's API reference from the per-operation JSON
Checks of api/tools/validate.mjs: (a)–(h) on each document, (i) across both (all pass)
CheckWhat it verifies
(a)YAML to JSON, with integers kept exactly (int64 tick values exceed 2^53)
(b)Validation against the official OAS 3.2 JSON Schemas, including every Schema and XML Object, with a self-test
(c)Unique operationIds, descriptions, request and response examples, x-verification with a matching badge tag, existing x-evidence paths, well-formed x-security-notes. Per-operation view: the SOAPAction const equals x-soap-action. Strict document: the SOAPAction enum equals the x-soap-operations actions and the oneOf lists match
(d)Every serializedValue is well-formed and byte-identical to its capture file
(e)Every XML example is walked against its schema: names, namespaces, prefixes, order, required members, i:nil, attributes, lexical types; a oneOf must match exactly one branch; multipart bodies part by part, including the exact header lines
(f)Every file under api/examples/ is referenced
(g)Leak scan for e-mail addresses and token-like strings
(h)Server URLs carry no query or fragment: no exception in the strict document; in the per-operation view only the URL and paths declared in x-oas-deviation
(i)The strict file equals build-strict(source) byte for byte, with the same SOAP actions, identical shared schemas, SOAP examples, example files and non-SOAP operations

Redocly CLI lints both documents: valid, 0 errors and 0 open warnings. The accepted warnings are listed per location, with reasons, in api/.redocly.lint-ignore.yaml: operations without a 2xx response (redirect-only pages, probes, dead updater URLs) and Redocly's composition heuristic on the two exclusive oneOfs. Conventions are explained in api/README.md.
