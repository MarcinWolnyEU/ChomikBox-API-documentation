Protocol - SOAP over HTTP, as it really works

  1. Overview
  2. Protocol

ChomikBox speaks SOAP 1.1 to one WCF service over plain HTTP, with gzip-compressed request bodies and the session token inside every body. Uploads, downloads and music streaming are separate HTTP requests to file servers that the SOAP calls name.

This page combines two sources. The behaviour of chomikbox.exe says what the client sends and reads. The live verification of 2026-10-24 says what the service accepts and returns; 17 of the 18 SOAP operations and all file-server endpoints were exercised. Where the two disagree, a box like this one shows both, and live wins:

Endpoint and SOAPAction dispatch

Two OpenAPI documents, and why ?op=

OpenAPI identifies operations by path and method, but the 17 main-service SOAP operations share one URL and one method (SessionBegin has its own host and path). A per-operation view gives each operation its own path key (/Auth, /Folders, …) under a path-level server http://box.chomikuj.pl/services/ChomikBoxService.svc?op=. Concatenated, the URL becomes ….svc?op=/Auth, which reaches the operation because WCF ignores the query string; a real path suffix would fail, as shown above. The real client posts to the bare .svc URL; both are equivalent. api/README.md

The project publishes two content-equivalent OpenAPI 3.2.1 documents, generated from the same source. api/chomikbox.openapi.yaml is the strictly conformant canonical document: SOAP is a single POST on /services/ChomikBoxService.svc with a SOAPAction enum and oneOf request and response bodies. api/chomikbox.per-operation.openapi.yaml is a per-operation view with one path item per SOAP operation, routed through a ?op= server URL; because a server URL may not contain a query, it declares that deviation in x-oas-deviation. The site's API reference is generated from api/chomikbox.per-operation.openapi.json.

Rules that matter for a client

  • Order matters. WCF reads parameters forward only: an out-of-order parameter is silently dropped (treated as null or 0), not rejected (S-06). The schemas list members in wire order. Live
  • The trailing slash matters. With the operation element in http://chomikuj.pl the parameters are not matched and the request faults (a:InternalServiceFault). Members in other namespaces are ignored. Live
  • Booleans: the client writes 0/1; true/false work equally. The s:encodingStyle attribute is optional. Omitted optional members and i:nil are both accepted.
  • The serializer has a <s:Header><Token> branch, but nothing enables it: the client never sends a SOAP header. Observed
Client
The client's SAX parser compares lower-cased local names and ignores prefixes and namespaces, so it reads every result by name.
Live
Two results use the datacontract namespaces shown above, and a few members exist that the client never reads (CheckEvents/new, which was nil in every probe, including 15 after the follow-up actions). A namespace-aware client must follow the table, not the client's habit.

Compression and headers

  • Requests. With [network] soap-use-gzip = true, set in the generic embedded defconf.ini, the body is gzip-compressed (zlib level -1, gzip wrapper) and sent with Content-Encoding: gzip; Content-Type stays text/xml;charset=utf-8. SessionBegin is always uncompressed. Observed
  • The service accepts gzip bodies. Live The captured Auth/success request was 249 bytes on the wire and 385 bytes uncompressed; Auth/success-uncompressed-request shows the plain variant.
  • Responses come back gzip-compressed when the request carries Accept-Encoding: gzip. Faults (HTTP 500) are never compressed. Live
  • The application sets none of these headers itself, so the defaults of the bundled Qt 4.8.5 apply: User-Agent: Mozilla/5.0 (no product token), Accept-Encoding: gzip (replies are unzipped transparently), Connection: Keep-Alive and Accept-Language: <locale>,en,* built from the Windows locale (a Polish system gives pl-PL,en,*; the C locale gives en,*). Observed for the Qt library, Inferred for the ChomikBox requests; the captures reproduce them. The one exception is the audio stream GET, which sends Accept-Encoding: with a single space.
  • Responses carry x-aspnet-version: 4.0.30319, x-powered-by: ASP.NET and an x-server node name (S-07). A typical SOAP round trip took 130–300 ms. Live

Session lifecycle - token, relogin, logout

  1. Auth. name, passHash (lower-case hex MD5 of the UTF-8 password, unsalted), ver = 4 and client{name = "chomikbox", version = "2.0.8.2"}. The constants are compiled in. It is sent at start-up (auto-login), after the system resumes and as the relogin. Observed (C-02)
  2. Outcomes. Ok with hamsterId, name and token; Forbidden for an unknown user; PermissionError for a wrong password (S-01). The service enforces neither ver nor client (S-11). Live
  3. Token. An opaque string, sent as the first child <token> of every later request except SessionBegin. There are no cookies, no HTTP authentication and no SOAP header (C-06).
  4. After login the client sends CheckEvents, starts its poll timer (see Settings, events and polling: 300 s idle, 60 s while uploading, 15 s while a folder view is open), requests Folders(0, 0), sends SessionBegin only if enabled, and flushes queued BoxEvents.
  5. BadToken. Any operation answers status = BadToken for an unknown or logged-out token. The client then runs Auth again, at most once per message, replaces the token in queued messages and resends them; session-bound messages are dropped.
  6. Logout invalidates exactly its own token; afterwards that token gets BadToken. The client sends it on quit and when the system suspends.
Client
The client keeps one token and replaces it on relogin.
Live
Several tokens of one account are valid at once, a new Auth does not invalidate earlier ones, and no expiry was seen within about 45 minutes (S-10). t is simply the Auth token; LoginFromBox?t=… turns it into a web session cookie. Whether it is accepted more than once was not measured.

Faults - HTTP 500

A fault is the service's answer to one request it could not process: HTTP 500 with a SOAP fault (xml:lang="en-US", never compressed). It is an unhandled exception for that request, not an outage; the service keeps serving other requests. Live

Because deserialization happens before an operation runs, the live work could use these faults with a fake token to learn every parameter name, type and order without side effects. The client logs faults as network errors and retries or relogs as described next.

Sequenced Download requests

With [network] sequence-soap = true (default config), Download entries are cut into parts of up to 2000. Each part carries sequence{stamp, part, count} with a shared random stamp, and the client waits for all parts before it acts. Observed

Client
The client always sends the sequenced form when sequence-soap is on.
Live
sequence is optional; the plain form works and then messageSequence is nil. A non-final part (part 0 of 2) is acknowledged with Ok, nil list and accountBalance, and only messageSequence echoed. The final part carries the data, including the entries of the earlier parts, but only under the conditions below. SavePlaylist also accepts an optional sequence.

The rules below fit all 26 sequenced exchanges of the follow-up (four sessions, tiny files of the test account). The behaviour is Live; the storage mechanism behind it is Inferred. They are also finding S-13.

  1. Entries of a non-final part are stored per session token, not per stamp, and by all origin nodes alike. A new part 0 replaces what was stored.
  2. The store is not cleared by the final part: a later final part sent alone, with a new stamp, still returns the earlier part's entry as well as its own.
  3. A final part returns the stored entries plus its own, grouped as usual. It is not a folder expansion: other files of the same folder are not listed.
  4. A final part with nothing stored in the session answers status = Error with a nil errorMessage and a nil list. A second login has its own, empty store.
  5. If the combined entries span two folders, the reply is Ok with an empty <a:list/>, even for the final part's own entry. A stale part from another folder empties a later final part in the same way.
  6. The agreements that count are those of the final message only: with own on both parts both entries got a signed URL; with own on part 0 only, neither did. Whether a final-message agreement is applied per entry or per type to all entries was not separated (Unknown).
  7. A single-message request (count = 1) ignores stored parts. In three-part sequences the middle part is acknowledged like part 0.

Consequence for clients: since the real client splits only above 2000 entries, normal requests are single messages. A request for more than 2000 files from more than one folder would come back empty, and two sequenced requests running at the same time in one session could mix their parts. Inferred

Settings, events, agreements and polling

CheckEvents polling

The client keeps a list of requested poll periods, and the timer uses the shortest one currently requested. The base entry comes from [proto-box] check-events-period (default config 300 s, application default 15 s); check-events-uploading-period (60 s) is added while the uploader is busy; check-events-folders-period (15 s) is added while a folder view exists. Adding a shorter period sends CheckEvents at once. Observed

Of a reply the client reads exactly three members, accountBalance, settings and changes (only folderModifyTime). new is never read, and neither is any other member; a non-nil new would be parsed and ignored. Observed Live, new was nil after every sandbox action (15 probes after uploads, ModifyFolder and SavePlaylist), so whether the service ever sends it is Unknown. Live

Settings

  • GetSettings is never sent by the client: nothing in it invokes the operation. Observed The operation is in the contract and works live; it is documented from the service side.
  • SetSettings is sent with downloadByBox = [downloader] enabled at start-up and every time the downloader applies its configuration. The opposite direction runs through CheckEvents: settings/downloadByBox is written back to the same key. settings contains only downloadByBox, in the client and live. Observed

BoxEvents

A small fixed set of events, not usage statistics and not gated by any setting: shutdown (poweroff, suspend or quit), detected.defaultplayer, settings.defaultplayer and settings.autostart (true/false). timestamp is 0. While logged out the list waits in [proto-box] box-events and is flushed after the next Auth. Observed Live, the service accepted settings.autostart = false and settings.defaultplayer = 0 with status = Ok, the same reply as for an empty list; whether it stores them is Unknown. Live (C-09)

Download: GET http://sNNNN.chomikuj.pl/File.aspx?e=…&pv=…

  • The signed URL comes from Download or RefreshFileUrl. GET returns the bytes with Content-Disposition: attachment; Range gives 206; HEAD is not supported (302 to /Error404.aspx). The file servers run IIS 10 and are not behind Cloudflare. Live
  • The same URL works again for a second GET (S-08). When a link expires the client calls RefreshFileUrl. expire was always nil live, so what the service sends is Unknown. The client parses it only from RefreshFileUrl, as the local-time string yyyy-MM-dd HH:mm:ss (a Unix time, an ISO T or a zone suffix is ignored), and ignores the expire of a Download entry. Observed It only feeds the warning when the user pauses downloads: [downloader] warn-before-expire is in seconds (default config 60, application default 3600), and the comparison looks inverted (now - expire), so the warning probably fires too often. Inferred
  • Music: the player fetches a player.audio URL with Icy-MetaData: 1 and Accept-Encoding: set to a single space, which disables Qt's gzip. It needs a 2xx, Content-Length greater than 0 and no x-nofile header. Live: 200 audio/mpeg, exact bytes, no ICY metadata.

Client vs live - summarised

The live findings confirmed the client's picture of the transport, the envelope and the session. They corrected it in places where the client reads more than the server sends, or sends something the server ignores:

  • ModifyFolder: the client's <public> flag does not exist on the server; the parameter is publicUpload. description, freePoints and freeTransfer are accepted and ignored (S-14).
  • AddFolder returns only folderId; RenameFolder, MoveFolder and RemoveFolder return only status/errorMessage.
  • FolderFiles items are <EntryInfo> with id, name, type, size, and type was only ever file (the client skips anything else); CheckEvents has an extra new that was never seen non-nil and that the client ignores.
  • The upload reply carries only res and fileid; the Download id form <hamsterId>/<folderId> makes the service fault; SessionBegin is not on the main service, and its host has no DNS record.

The full register, as recorded in the OpenAPI document, is on the API reference.
